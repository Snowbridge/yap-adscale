## Функциональные

Функциональные, судя по всему, не отличаются заметно от таковых до интеграции, т.к. что раньше делал AdScale, то и дальше должен, а вся проблема сконцентрирована в атрибутов качетсва, т.к. в текущем варианте архитектуры AdScale с масштабированием не справится.

### RTB и интеграция с DSP

- **FR-1** — Система принимает **запросы на ставку** от DSP-партнёра по согласованному протоколу обмена (**HTTPS**, **OpenRTB** или эквивалентному контракту).
- **FR-2** — Для каждого запроса выполняется **идентификация/обогащение контекста** (пользователь, площадка, формат креатива) в рамках существующей модели таргетинга AdScale.
- **FR-3** — Система **отбирает кандидатов** рекламы и передаёт их в механизм аукциона/ставок с теми же бизнес-правилами, что и для текущих источников спроса.
- **FR-4** — Система формирует **ответ на запрос ставки** (размер ставки, рекламный материал и метаданные, идентификаторы) в срок, заданный соглашением об уровне обслуживания с партнёром и внутренними лимитами.
- **FR-5** — При отсутствии подходящей рекламы или при срабатывании защитных лимитов система возвращает **корректный отказ** без нарушения контракта.
- **FR-6** — Победы в аукционах, инициированных через DSP, **учитываются в биллинге**: списание бюджета, лимиты кампаний, финансовая согласованность с Financial Service.

### Выдача рекламы и события

- **FR-7** — После выигрыша аукциона **Delivery Service** формирует разметку/ответ для показа на площадке партнёра или через существующую цепочку выдачи.
- **FR-8** — **Показы и клики** по кампаниям, пришедшим через DSP, регистрируются в статистике с привязкой к кампании, рекламодателю и источнику demand.
- **FR-9** — Данные событий доступны для **отчётности в рекламном кабинете** и операционной аналитики (с допустимой задержкой для некритичного контура).

### Управление и существующие клиенты

- **FR-10** — Рекламодатели через **личный кабинет** по-прежнему создают и управляют кампаниями, бюджетами и ставками; интеграция с DSP не требует отдельного UI для партнёра на стороне AdScale (если не оговорено отдельно).
- **FR-11** — **Пополнение бюджета** и операции с платёжным шлюзом работают без регрессии.
- **FR-12** — Существующие каналы размещения и аукционов **продолжают работать** параллельно с трафиком DSP (единая платформа, общие правила взвешивания).

### Эксплуатация и контроль

- **FR-13** — Для интеграции доступны **метрики и трассировка**: RPS по партнёру, latency, ошибки, no-bid rate, таймауты.
- **FR-14** — Допускается **поэтапное включение** трафика DSP (canary/процент трафика) без остановки монолита.

## Атрибуты качества

### P1 — критично для успеха интеграции и штрафных SLA

- **Производительность (latency)**
  - Целевое состояние: P95 времени ответа на bid path **≤ 100 ms** (внутренний SLA); устойчивое время ответа для партнёра **≤ 80 ms** без систематических нарушений
  - Комментарий: Главный драйвер проигрыша аукционов и штрафов
- **Доступность критического пути**
  - Целевое состояние: Bidding/Auction path без аварийных простоев в часы пик; восстановление при сбоях без потери контрактной работоспособности
  - Комментарий: Штрафы за downtime
- **Пропускная способность**
  - Целевое состояние: **≥ 18 000 RPS** на аукционном/RTB контуре в пик без деградации SLA
  - Комментарий: +20% к текущему пику

### P2 — важно в горизонте 3 месяцев

- **Масштабируемость**
  - Целевое состояние: Возможность **горизонтально масштабировать** наиболее нагруженные компоненты (Ad Server, bidding/auction)
  - Комментарий: Подготовка к ~50 000 RPS к году
- **Надёжность / устойчивость**
  - Целевое состояние: Изоляция сбоев: перегрузка статистики/аналитики **не блокирует** аукцион
  - Комментарий: Связано с разделением потоков
- **Согласованность данных (финансы)**
  - Целевое состояние: Корректное списание и отсутствие «двойных» списаний при пиковой записи событий
  - Комментарий: Транзакционный контур остаётся строгим
- **Наблюдаемость**
  - Целевое состояние: Метрики, алерты по SLO latency/RPS/ошибкам, в т.ч. по DSP
  - Комментарий: Компенсация отсутствия SRE за счёт простых дашбордов

### P3 — целевое развитие до 12 месяцев

- **Модифицируемость / эволюция**
  - Целевое состояние: Поэтапное выделение сервисов без остановки бизнеса
  - Комментарий: Strangler, ADR
- **Безопасность**
  - Целевое состояние: Защита API интеграции (TLS, аутентификация партнёра), безопасность платежей и ПДн по текущим нормам
  - Комментарий: Базовый уровень для B2B API
- **Доступность платформы (end-to-end)**
  - Целевое состояние: Движение к **99,9%** SLA на горизонте года, мультирегион
  - Комментарий: Не первичный фокус первых 3 месяцев при одном кластере

**Сводный порядок приоритетов:** производительность и доступность RTB → пропускная способность → масштабируемость и изоляция потоков → финансовая согласованность и observability → долгосрочная модифицируемость и гео-отказоустойчивость.
