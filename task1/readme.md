## Целевое решение (тезисы)

Платформа **больше не монолит**: она состоит из **четырёх подсистем**, по одной на каждый bounded context из [`03-bounded-contexts.md`](03-bounded-contexts.md). Внутри каждой подсистемы — **микросервисы** (на текущем уровне документации не детализируются). У каждой подсистемы — **собственное хранилище данных** (database per subsystem).

Интеграция между подсистемами — **событийная (Kafka)** плюс точечный синхронный REST для некритичных UI-сценариев. Детали топиков и edge — на диаграмме [`diagrams/05-c4-container-to-be.puml`](diagrams/05-c4-container-to-be.puml) и в ADR.

### 1. Входной контур (API Gateway)

На входе — **шлюз(и) edge**, которые **сегрегируют** входящий трафик на два потока (см. также [ADR-005](ADR/ADR-005-dual-edge-gateway.md)):

1. **Bid request** (DSP, SSP, выдача) направляется в подсистему **«Аукционы и Выдача рекламы»**.
2. **Телеметрия** (показы, клики, beacon’ы) направляется в контур приёма событий и далее в **Kafka** (топик входящей телеметрии, например `telemetry.events`) для учёта всеми заинтересованными подсистемами.

Отдельно от hot path обслуживается **API рекламодательских UI** (кабинет и отчётность) через **API Gateway (UI)** — без смешения с RTB-потоком.

### 2. Подсистема «Аукционы и Выдача рекламы»

- Критический путь аукциона и выдачи рекламы.
- **Читает и пишет только Redis** (кэш/оперативное состояние): правила торгов, кандидаты, лимиты, балансы взаиморасчётов, счётчики показов/кликов, шаблоны контента и т.д.
- **С PostgreSQL эта подсистема не работает** — все данные для торгов берутся из Redis.
- Для **актуализации Redis** подсистема **подписывается на топики Kafka**, в которые публикуют исходящие события остальные подсистемы (конфигурация кампаний, балансы, телеметрия для счётчиков и др.).
- Собственные события аукциона (bid / win / no-bid) при необходимости публикует в Kafka для наблюдаемости и аналитики.

### 3. Подсистема «Управление кампаниями и ставками»

- **UI для рекламодателей**: кампании, бизнес-правила участия в торгах, лимиты, бюджеты, шаблоны контента.
- Персистентность — **своя PostgreSQL**.
- **Подписка на топики телеметрии**: чтение **батчами**, агрегация (суммирование по кампаниям/периодам), запись агрегатов в свою БД (контроль лимитов и расхода; источник агрегатов для биллинга — [ADR-003](ADR/ADR-003-billing-spend-aggregates-source.md)).
- **Публикация в Kafka** изменений лимитов, бюджетов, правил торгов, шаблонов; подсистема аукционов потребляет эти события и **обновляет Redis**.

### 4. Подсистема «Финансы и Биллинг»

- Биллинг, инвойсирование, учёт и сверка взаиморасчётов.
- **Своя PostgreSQL** (строгий ACID-контур).
- **Публикация в Kafka** сообщений об изменении **состояния взаиморасчётов** (например, топик `billing.balance`); их потребляют подсистемы **«Управление кампаниями и ставками»** и **«Аукционы и Выдача рекламы»** (остатки, остановка кампаний, актуализация кэша на hot path).

### 5. Подсистема «Телеметрия и Отчётность»

- Приём потока событий через Kafka (та же входящая телеметрия, что и у других потребителей).
- **Хранение сырых событий** — в **ClickHouse** (по одному событию на запись).
- **Агрегация** для OLAP-отчётности (materialized views / агрегаты в аналитическом хранилище); агрегаты отчётности **не смешиваются** с финансовыми агрегатами кампаний (разная семантика и разрезы).
- **UI отчётности**: построение отчётов, настройка расписаний, **автоформирование и рассылка** (в т.ч. через внешний email-сервис).
